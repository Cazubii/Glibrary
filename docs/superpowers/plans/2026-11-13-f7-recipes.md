# F7 — Receitas guiadas Implementation Plan

> Execute inline, com uma receita por vez. Esta frente é um PR incremental separado sobre F6.

**Goal:** Conduzir uma pessoa iniciante da escolha de um modelo até uma execução de agente, da URL do GitHub à pergunta para um agente, e de uma pasta local ao primeiro envio para o GitHub.

**Architecture:** A tela Início abre um assistente com três receitas canceláveis e passo atual visível. Operações locais e GitHub continuam no processo principal, com Zod no IPC e respostas `{ ok, data | error }`. Reaproveitar clone de Base, análise GitHub, coleções, perfis de agente e revisão Git existentes. Para publicar, salvar localmente a primeira versão antes de criar o remoto; torná-lo privado por padrão e só enviar depois de confirmação explícita.

**Tech Stack:** Electron, TypeScript estrito, React, Zod, simple-git, Vitest.

---

## Diagnóstico confirmado antes de mudar

- `DashboardPage` já é a tela Início e aceita atalhos para Projetos, Ferramentas e Agentes, mas não mostra receitas.
- `api.baseClone` baixa uma Base em `settings.basesRoot`; `api.projectAdd` registra o caminho como projeto; `api.kitApply` associa uma Coleção (Kit) ao projeto.
- A entidade `Repo` é diferente de `ProjectRef`: perfis e execuções de agente usam `Repo`, então um projeto de Base precisa ser registrado também por `api.repoAddLocal`.
- `RepoAnalysisPage` já analisa URL pública e `api.repoAddByUrl` já consegue iniciar um clone em segundo plano. `api.onStatusChanged` sinaliza conclusão/erro.
- `AgentesPage` cria perfis e execuções; `AGENT_CLI_PRESETS` lista Claude Code, OpenCode, Codex CLI, Gemini CLI e Aider. Não há recomendação definida nem detecção geral dessas CLIs; a receita exige escolha explícita, sem preseleção.
- O Git local permite revisar diff, criar commit e enviar se houver um remoto. Falta inicializar Git de forma assistida, criar um repositório GitHub e anexar o remoto.
- O instalador já empacota `resources/**`; um modelo estático embutido pode ser copiado no main para uma pasta nova sem dependências ou migração do `library.json`.
- O GitHub REST `POST /user/repos` aceita GitHub App user access tokens com a permissão `Repository creation: write`; o token do GitHub App configurado atualmente não tem essa permissão. PAT clássico precisa de `public_repo` para público ou `repo` para privado. A implementação deve explicar essa limitação sem ampliar permissões por conta própria.

## Decisões desta frente

1. Exibir as três receitas em Início e abrir um assistente modal que mantenha o passo visível, permita voltar/cancelar e não apague pastas, commits ou remotos ao cancelar.
2. No primeiro site, clonar a Base escolhida, registrar a pasta tanto como `ProjectRef` quanto `Repo`, associar uma Coleção escolhida se houver e criar perfil de agente somente após a pessoa escolher uma CLI.
3. Na análise, mostrar os resultados existentes, permitir clonar o repositório e só então oferecer a pergunta ao agente. O clone segue o gerenciador de progresso atual; cancelar a receita não apaga o clone.
4. Na publicação, iniciar Git somente na própria pasta escolhida e recusar pastas dentro de outro repositório; revisar e salvar a primeira versão local antes de criar remoto. Criar privado por padrão; público exige seleção e aviso explícito.
5. Criar o repositório em `POST /user/repos`, sem README remoto automático, validar a resposta, adicionar `origin` HTTPS sem token na URL, persistir o remote e enviar com o helper temporário de autenticação já usado pelo GitService.
6. Se o GitHub negar a permissão de criação, manter o commit local e explicar opções: PAT avançado com escopo mínimo apropriado ou mantenedor conceder `Repository creation: write` ao GitHub App e pedir nova autorização. Não registrar nem alterar app.
7. Não definir CLI recomendada nesta frente; a seleção permanece sem valor inicial até decisão do mantenedor. A receita informa que a CLI precisa estar instalada.

## Critérios de aceite

- As três receitas começam em Início, mostram progresso atual e podem ser canceladas sem apagar trabalho existente.
- Uma Base pode virar projeto local associado a uma Coleção escolhida quando houver coleções cadastradas; numa biblioteca vazia, o modelo embutido permite iniciar sem configuração prévia.
- Uma URL GitHub pode ser analisada, baixada e enviada a um agente com pergunta do usuário.
- Uma pasta local pode ser revisada, receber primeira versão, criar repo remoto privado por padrão e enviar a primeira versão; público só após aviso/confirmação.
- A publicação funciona com um PAT que tenha permissão adequada; o login App continua dependente do mantenedor habilitar a permissão mínima `Repository creation: write`.
- Nenhuma credencial é gravada em URL/config/log; IPC mantém Zod e `{ ok, data | error }`.
- Typecheck, lint, testes, build e CI Windows/Linux/macOS passam.
